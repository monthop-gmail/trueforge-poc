# คำถามถึงผู้ให้บริการ gateway — ร่างไว้ ยังไม่ส่ง

เตรียมตาม dis-bc779b20 seq 39 ข้อ 6 (TrueFoundry) และ seq 44 (Smithery) ·
**ยังไม่ติดต่อผู้ให้บริการรายใดและยังไม่เปลี่ยน config ใด ๆ** จนกว่าเจ้าของบัญชีจะสั่ง ·
ในใบนี้ไม่มีชื่อ tenant ชื่อโฮสต์จริง key หรือ credential

ถามสองเจ้าด้วยคำถามชุดเดียวกันโดยตั้งใจ — ถ้าตอบต่างกัน เราเลือกได้ ถ้าตอบเหมือนกัน แปลว่า
ข้อจำกัดนี้เป็นของตลาด ไม่ใช่ของเจ้าใดเจ้าหนึ่ง ซึ่งเป็นคำตอบที่มีค่าพอกัน

## ทำไมถึงถาม

เราต้องการให้ระบบปลายทางได้รับโทเคนที่ **ผูกกับปลายทางนั้นจริง** และบอกได้ว่าผู้เรียกเป็นใคร
วันนี้ gateway ทำได้สามอย่าง และไม่มีอันไหนให้ทั้งสองอย่างพร้อมกัน

| โหมด | ตัวตนรายคน | audience ผูกกับปลายทาง | ใช้งานได้จริงวันนี้ |
| --- | --- | --- | --- |
| header credential ที่ใช้ร่วมกัน | ไม่ได้ | ไม่เกี่ยว | ได้ |
| passthrough | ได้ (ตรวจลายเซ็นได้ มี `sub`) | **ไม่** | ได้ แต่ไม่ควรใช้ |
| outbound OAuth | ได้ | ได้ | **ต่อไม่ได้** |

# ส่วนที่หนึ่ง — ถึง TrueFoundry

## คำถามที่ 1 — outbound OAuth รองรับ PKCE เมื่อไรและอย่างไร

**อาการ** ตอนที่ gateway ทำ authorization-code flow ไปยัง MCP server ปลายทาง มันไม่ส่ง
`code_challenge` ปลายทางที่บังคับ PKCE จึงปฏิเสธตั้งแต่ขั้น authorize

**ทำซ้ำได้อย่างไร** ตั้ง connector เป็น `oauth2` + `authorization_code` ชี้ไป MCP server ที่
ประกาศ `code_challenge_methods_supported: ["S256"]` แล้วเริ่ม flow

**หลักฐานฝั่งเรา** ปลายทางที่ทดสอบสองตัว บังคับ PKCE จริงทั้งคู่ — ยิง `/authorize` โดยไม่ส่ง
`code_challenge` ได้ `400` และส่ง `S256` ได้ `200` · ส่วนฝั่ง gateway เมื่อขอ authorize URL
ออกมา ไม่มีพารามิเตอร์ `code_challenge` อยู่ในนั้น

**สิ่งที่อยากได้** ทราบว่ารองรับแล้วหรือยัง ถ้ายัง มีแผนหรือไม่ และถ้ามีวิธีเปิดใช้ต้องตั้งค่าตรงไหน

## คำถามที่ 2 — รองรับ RFC 8693 token exchange หรือ resource-bound token หรือไม่

**อาการ** โหมด passthrough ส่งโทเคนของผู้เรียกไปยังปลายทางตามเดิม ซึ่งตรวจสอบตัวตนได้จริง
แต่ `aud` ของโทเคนชี้ไปที่ tenant/application ของ gateway ไม่ใช่ทรัพยากรของปลายทาง และเป็น
ค่าเดียวกันทุก MCP server ใน tenant · ถ้าปลายทางตั้งรับ audience นั้น โทเคนที่ออกให้ระบบอื่น
ใน tenant เดียวกันจะใช้ข้ามมาได้ เราจึงไม่ตั้ง

**ทำซ้ำได้อย่างไร** ยิง token endpoint ของ authorization server ด้วย
`grant_type=urn:ietf:params:oauth:grant-type:token-exchange` พร้อม `subject_token`,
`subject_token_type` และ `resource` ที่ชี้ไปปลายทาง

**หลักฐานฝั่งเรา** ได้กลับมา `422` พร้อมข้อความว่า grant_type รับได้เฉพาะ
`authorization_code` กับ `refresh_token` · และ metadata ของ authorization server ประกาศ
grant ไว้ห้าแบบ (มี `password`, `implicit`, `device_code` ด้วย) ซึ่งไม่ตรงกับสิ่งที่ token
endpoint รับจริง

**สิ่งที่อยากได้** ทราบว่ามีวิธีให้ปลายทางได้โทเคนที่ `aud` หรือ `resource` เป็นของปลายทางเองหรือไม่
ไม่ว่าจะด้วย token exchange หรือกลไกอื่น · และถ้าไม่มี แนะนำอย่างไรสำหรับปลายทางที่ต้องตรวจ
audience ตามสเปกของ MCP

# ส่วนที่สอง — ถึง Smithery

บริบท: ทดลองต่อ MCP server ของเราเองผ่าน REST API สำเร็จ และ read-only enforcement ของ
ปลายทางยังทำงานผ่าน gateway ได้ถูกต้อง · สามคำถามข้างล่างคือสิ่งที่ยังตอบไม่ได้จากการทดลอง

## คำถามที่ 1 — คำสั่งฝั่ง connection ของ CLI ตอบ 404 ทุกคำสั่ง

**อาการ** `mcp list`, `mcp get`, `mcp add` ตอบ `404 Server not found` ทุกครั้ง ขณะที่ REST API
ตัวเดียวกันทำงานปกติด้วยโทเคนใบเดียวกัน · คำสั่งที่ไม่เกี่ยวกับ connection เช่น `mcp search`
ทำงานได้ตามปกติ

**ทำซ้ำได้อย่างไร** ล็อกอินด้วย `auth login` จนสำเร็จ (CLI รายงาน organization และ namespace
ถูกต้อง) แล้วเรียก `mcp list`

**สิ่งที่ตัดออกไปแล้ว** ทดสอบก่อนและหลังล็อกอิน · ทั้ง API key และโทเคนที่ได้จากการล็อกอิน ·
ทั้งแพ็กเกจ `@smithery/cli` และ `smithery` · ระบุ `--namespace` ตรง ๆ · ตั้ง env ชี้ base URL
ของ API — ได้ 404 เหมือนกันทุกกรณี

**เบาะแสที่พอมี** `GET /connect/<namespace>` ตอบ 200 แต่ `GET /connect` ที่ไม่มี namespace
ตอบ 404 · เดาว่า CLI เรียกเส้นหลัง

**ทำไมถึงสำคัญกับเรา** uplink คือสิ่งเดียวที่ทำให้ MCP server ในเครือข่ายภายในของเราถูกเรียกจาก
คลาวด์ได้โดยไม่ต้องเปิดทางเข้า และ CLI คือฝ่ายที่ต้องเปิด WebSocket ขาออก · REST API สร้าง
connection แบบ `uplink` ได้จริง (`transport` รับ `http` กับ `uplink`) แต่ค้างที่ `disconnected`
เพราะไม่มีฝั่งเอเจนต์มาต่อ

**สิ่งที่อยากได้** เป็นบั๊กหรือเป็นการตั้งค่าที่เราพลาด · ถ้าเป็นบั๊ก มีเวอร์ชันที่ใช้ได้ไหม ·
หรือมีวิธีเปิด uplink โดยไม่ผ่าน CLI

## คำถามที่ 2 — outbound OAuth รองรับ PKCE (S256) หรือไม่

**ทำไมถึงถาม** MCP server ปลายทางของเราบังคับ PKCE ทั้งสองตัว — เรียก `/authorize` โดยไม่ส่ง
`code_challenge` ได้ 400 และส่ง S256 ได้ 200 · gateway อีกเจ้าที่ทดสอบไม่ส่ง `code_challenge`
ในขา outbound จึงต่อกับปลายทางของเราไม่ได้เลย

**สิ่งที่อยากได้** ถ้า gateway ทำ authorization-code flow ไปยัง MCP server ที่บังคับ PKCE
จะส่ง `code_challenge` ให้หรือไม่ และตั้งค่าตรงไหน

## คำถามที่ 3 — มี resource-bound token หรือ token exchange หรือไม่

**ทำไมถึงถาม** เราต้องการให้โทเคนที่ปลายทางได้รับมี `aud` หรือ `resource` เป็นของปลายทางเอง
ไม่ใช่ของ gateway · การให้ปลายทางยอมรับ audience ที่เป็นของ gateway จะทำให้โทเคนที่ออกให้
ระบบอื่นในบัญชีเดียวกันใช้ข้ามมาได้ ซึ่งเป็นสิ่งที่เราจะไม่ทำ

**สิ่งที่อยากได้** มีกลไกออกโทเคนที่ผูกกับปลายทางหรือไม่ ไม่ว่าจะด้วย RFC 8693 token exchange
หรือวิธีอื่น · ถ้าไม่มี แนะนำอย่างไรสำหรับปลายทางที่ต้องตรวจ audience ตามสเปกของ MCP

# ข้อควรระวังตอนส่ง — ใช้กับทั้งสองเจ้า

ส่งจากบัญชีของเจ้าของ tenant หรือเจ้าของ workspace · ไม่แนบโทเคน ไม่แนบ key ไม่แนบ log ดิบ
ไม่แนบชื่อโฮสต์ภายในที่ไม่จำเป็น · อ้างพฤติกรรมที่ทำซ้ำได้แทนการแนบ evidence ที่มีค่าจริง ·
ถ้าเขาขอ log ให้ sanitize ก่อนทุกครั้ง
