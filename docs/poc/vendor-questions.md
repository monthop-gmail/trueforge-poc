# คำถามสองข้อถึงผู้ให้บริการ gateway — ร่างไว้ ยังไม่ส่ง

เตรียมตาม dis-bc779b20 seq 39 ข้อ 6 · **ยังไม่ติดต่อผู้ให้บริการและยังไม่เปลี่ยน config ใด ๆ**
จนกว่าเจ้าของบัญชีจะสั่ง · ในใบนี้ไม่มีชื่อ tenant ชื่อโฮสต์จริง หรือ credential

## ทำไมถึงถาม

เราต้องการให้ระบบปลายทางได้รับโทเคนที่ **ผูกกับปลายทางนั้นจริง** และบอกได้ว่าผู้เรียกเป็นใคร
วันนี้ gateway ทำได้สามอย่าง และไม่มีอันไหนให้ทั้งสองอย่างพร้อมกัน

| โหมด | ตัวตนรายคน | audience ผูกกับปลายทาง | ใช้งานได้จริงวันนี้ |
| --- | --- | --- | --- |
| header credential ที่ใช้ร่วมกัน | ไม่ได้ | ไม่เกี่ยว | ได้ |
| passthrough | ได้ (ตรวจลายเซ็นได้ มี `sub`) | **ไม่** | ได้ แต่ไม่ควรใช้ |
| outbound OAuth | ได้ | ได้ | **ต่อไม่ได้** |

## คำถามที่ 1 — outbound OAuth รองรับ PKCE เมื่อไรและอย่างไร

**อาการ** ตอนที่ gateway ทำ authorization-code flow ไปยัง MCP server ปลายทาง มันไม่ส่ง
`code_challenge` ปลายทางที่บังคับ PKCE จึงปฏิเสธตั้งแต่ขั้น authorize

**ทำซ้ำได้อย่างไร** ตั้ง connector เป็น `oauth2` + `authorization_code` ชี้ไป MCP server ที่
ประกาศ `code_challenge_methods_supported: ["S256"]` แล้วเริ่ม flow

**หลักฐานฝั่งเรา** ปลายทางที่ทดสอบสองตัว บังคับ PKCE จริงทั้งคู่ — ยิง `/authorize` โดยไม่ส่ง
`code_challenge` ได้ `400` และส่ง `S256` ได้ `200` · ส่วนฝั่ง gateway เมื่อขอ authorize URL
ออกมา ไม่มีพารามิเตอร์ `code_challenge` อยู่ในนั้น

**สิ่งที่อยากได้** ทราบว่ารองรับแล้วหรือยัง ถ้ายัง มีแผนหรือไม่ และถ้ามีวิธีเปิดใช้ต้องตั้งค่าตรงไหน

## คำถามที่ 2 — รองรับ RFC 8693 token exchange หรือ resource-bound token หรือไม่

**อาการ** โหมด passthrough ส่งโทเคนของผู้เรียกไปยังปลายทางตามเดิม ซึ่งตรวจสอบตัวตนได้จริง
แต่ `aud` ของโทเคนชี้ไปที่ tenant/application ของ gateway ไม่ใช่ทรัพยากรของปลายทาง และเป็น
ค่าเดียวกันทุก MCP server ใน tenant · ถ้าปลายทางตั้งรับ audience นั้น โทเคนที่ออกให้ระบบอื่น
ใน tenant เดียวกันจะใช้ข้ามมาได้ เราจึงไม่ตั้ง

**ทำซ้ำได้อย่างไร** ยิง token endpoint ของ authorization server ด้วย
`grant_type=urn:ietf:params:oauth:grant-type:token-exchange` พร้อม `subject_token`,
`subject_token_type` และ `resource` ที่ชี้ไปปลายทาง

**หลักฐานฝั่งเรา** ได้กลับมา `422` พร้อมข้อความว่า grant_type รับได้เฉพาะ
`authorization_code` กับ `refresh_token` · และ metadata ของ authorization server ประกาศ
grant ไว้ห้าแบบ (มี `password`, `implicit`, `device_code` ด้วย) ซึ่งไม่ตรงกับสิ่งที่ token
endpoint รับจริง

**สิ่งที่อยากได้** ทราบว่ามีวิธีให้ปลายทางได้โทเคนที่ `aud` หรือ `resource` เป็นของปลายทางเองหรือไม่
ไม่ว่าจะด้วย token exchange หรือกลไกอื่น · และถ้าไม่มี แนะนำอย่างไรสำหรับปลายทางที่ต้องตรวจ
audience ตามสเปกของ MCP

## ข้อควรระวังตอนส่ง

ส่งจากบัญชีของเจ้าของ tenant · ไม่แนบโทเคน ไม่แนบ log ดิบ ไม่แนบชื่อโฮสต์ภายในที่ไม่จำเป็น ·
อ้างพฤติกรรมที่ทำซ้ำได้แทนการแนบ evidence ที่มีค่าจริง
