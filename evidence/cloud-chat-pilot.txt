== 5. stop conditions — ตรวจครบ ไม่มีข้อใดเกิดขึ้น ==
write tool ทำงานสำเร็จ            : ไม่เกิด (ถูกปฏิเสธครบเก้าตัว)
credential ข้ามเส้นทางได้          : ไม่เกิด (พิสูจน์ไว้แล้วใน acceptance 21/21)
gateway ไม่ปฏิเสธผู้ไม่มีสิทธิ์     : ไม่เกิด (ข้อ 4)
มีคำขอไปถึง ws-001 หรือข้อมูลไซต์  : ไม่เกิด — connector ชี้ไป host ของ deployment ทดสอบเท่านั้น
                                     และ workspace ทดสอบยังมี discussions=1 เท่าเดิมหลังจบ pilot
                                     คือไม่มีอะไรถูกเขียนเพิ่มจากการทดสอบรอบนี้

== สิ่งที่รอบนี้ยังไม่ได้พิสูจน์ ==
การต่อจากไคลเอนต์แชทบนคลาวด์ของจริง (login/consent ในตัวแอป) ยังไม่ได้ทำ
เพราะต้องให้เจ้าของงานเพิ่ม connector ในแอปด้วยบัญชีตัวเอง
สิ่งที่พิสูจน์แล้วคือชั้นโปรโตคอลทั้งหมดที่ไคลเอนต์เหล่านั้นใช้ — 401 พร้อม WWW-Authenticate,
protected-resource metadata, AS metadata ที่มี DCR และ PKCE S256 และ DCR จริงที่ตอบ 201
(บันทึกไว้ตั้งแต่ seq 9) รวมถึงเส้นทางทั้งหมดในไฟล์นี้

== ข้อจำกัดที่ต้องระบุคู่กับผลเสมอ ==
upstream เห็นตัวตนของ credential ที่ใช้ร่วมกัน ไม่ใช่ตัวผู้ใช้รายคน
การแยกรายคนมีหลักฐานอยู่ที่ gateway เท่านั้นใน pilot นี้

== 6. ต่อจากไคลเอนต์แชทบนคลาวด์จริง — ทำแล้วโดยเจ้าของงาน ==
เจ้าของงานเพิ่ม connector ในแอปด้วยบัญชีตัวเอง ต่อติดและเรียกใช้ได้จริง ไม่มี error เรื่อง auth
tool ที่ไคลเอนต์มองเห็น: get_workspace_context, get_tasks, get_decisions, get_plans,
                        get_handoffs, get_discussion  (หกตัว ตรงกับที่อนุมัติ)
get_workspace_context : เรียกสำเร็จ ได้ข้อมูลจริง ไม่ใช่แค่ชื่อ tool ในรายการ

== 7. ข้อสังเกตสองข้อจากผลของไคลเอนต์จริง ==

ก. identity ที่ไคลเอนต์เห็นคือ "Static bearer"
   ตรงกับข้อจำกัดที่ประกาศไว้ทุกครั้ง: upstream เห็นตัวตนของ credential ที่ใช้ร่วมกัน
   ไม่ใช่ตัวผู้ใช้รายคน · ผู้ใช้ที่มองจากแอปจึงเห็นป้ายเดียวกันหมด ไม่ว่าจะเป็นใคร

ข. id ของ workspace ซ้ำกันระหว่าง deployment
   deployment ทดสอบรายงาน id "ws-001" ชื่อ "Workspace #001" มี discussion เดียวคือ
   ตัวที่ probe ของเราสร้าง participants 0
   ส่วนโต๊ะจริงก็ใช้ id "ws-001" เหมือนกัน แต่ชื่อ "งานจริงของทีม" มี participants 23
   และ discussion 26 รายการ
   สาเหตุ: schema.sql seed workspace ตั้งต้นด้วย id เดียวกันทุก deployment

   ผลที่ตามมา — **id อย่างเดียวแยกไม่ออกว่าอยู่ deployment ไหน** คนที่อ่านจากแอปเห็นคำว่า
   ws-001 แล้วเข้าใจว่าเป็นโต๊ะจริงได้ทันที ทั้งที่เป็นคนละฐาน
   ตัวที่แยกได้จริงคือ ชื่อ workspace, จำนวน participants และรายการ discussion

   pilot รอบนี้ไม่ได้แตะโต๊ะจริง ยืนยันจากสามอย่างนั้นและจากที่ connector ชี้ไป host
   ของ deployment ทดสอบเท่านั้น แต่เกณฑ์หยุดที่เขียนว่า "ไม่มีคำขอไปถึง ws-001"
   ควรแก้ถ้อยคำให้ชี้ที่ deployment ไม่ใช่ที่ id เพราะ id ซ้ำกันได้
